### D-001 後端模組格式與測試框架：ESM＋Vitest

- **日期：** 2026/10/22 E 提案；2026/10/25 寫入 PRD v0.5.9
- **決定：** 後端照 Nest 12 `nest new` 的預設，使用 ESM＋Vitest，不手動改成 CJS＋Jest；整合測試用 Vitest＋Supertest。PRD 第十九節的測試框架從 Jest 改為 Vitest。
- **原因：**
  - Nest 12 的 `nest new` 預設就是 ESM＋Vitest，CLI 沒有選項可以改成 CJS＋Jest；Prisma 7 的 `prisma-client` generator 預設也產生 ESM。照預設走，自己要維護的設定最少，之後升級或查問題比較容易。
  - Vitest 的 `describe`、`it`、`expect` 寫法和 Jest 幾乎相同，Supertest 照用；Jest 對 ESM 的支援還在實驗階段，基本上要搭 CJS。ESM 配 Vitest、CJS 配 Jest，兩組綁在一起，不混搭。
  - 已實測（2026/10/22，`@nestjs/cli@12.0.10`）：build、依賴注入、單元測試、整合測試都能正常執行。
- **沒有採用的方案：** CJS＋Jest。要手動改樣板（拿掉 `"type": "module"`、改 tsconfig、安裝 Jest 與 ts-jest 並改寫設定），D 的 Prisma schema 也要在 `generator client` 加 `moduleFormat = "cjs"`。
- **代價：**
  - 網路上的 Nest 教學多半是 CJS＋Jest 寫法，照抄時要改。
  - 相對路徑 import 要寫 `.js`（例如 `import { AppService } from './app.service.js'`）；`__dirname` 改用 `import.meta.dirname`；mock 用 `vi.fn()`。
  - 少數只支援 CJS 的舊套件要另外處理。
- **誰同意：** C、D、E（後端組三人都同意後才採用）
- **參考：** E〈後端模組格式與測試框架比較（ESM＋Vitest vs. CJS＋Jest）〉v0.1（2026/10/22）；寫法慣例見 `backend/README.md` 的「開發慣例」

### D-008 JWT 驗證不用 Passport，改用自己寫的全域 guard

- **日期：** 2026/10/27
- **決定：**
  - 只用 `@nestjs/jwt` 簽發與驗證 token，guard（`JwtAuthGuard`）自己寫，不裝 `@nestjs/passport`、`passport-jwt`（PRD 第七節原本寫「`@nestjs/jwt`＋Passport」）。
  - guard 用 `APP_GUARD` 註冊成全域：每個端點預設都要登入，公開端點加 `@Public()`。
  - token 只帶 `sub`（使用者 id），HS256、有效 24 小時；guard 不查資料庫，`@CurrentUser()` 只有 `id`。
- **原因：**
  - 只有一種登入方式（Email＋密碼），Passport 的「多種 strategy」用不到，多 2 個套件與一層設定反而難懂。
  - 全域 guard 不會漏加：新端點忘了加 `@UseGuards` 也一樣要登入。
  - P0 沒有刪除帳號的功能，token 對應的使用者不會消失，所以不用每個請求都查一次資料庫。
- **誰同意：** D 提出（PR AUTH-1），待 E 審查 PR 時確認
- **影響：** C、E 的端點不用加任何 guard；實作時在參數加 `@CurrentUser() user: AuthUser`。

### D-009 密碼雜湊用原生的 bcrypt@6，不用 bcryptjs

- **日期：** 2026/10/29（10/31 依 E 審查 PR #42 的建議，由 bcryptjs 改成 bcrypt@6）
- **決定：**
  - 密碼雜湊用 `bcrypt@6`（原生套件），不用純 JavaScript 的 `bcryptjs`。演算法同樣是 bcrypt（PRD 第七節、FR-02），雜湊格式相同（`$2b$10$…`）。
  - 成本固定 10。
- **原因：**
  - `bcryptjs` 的雜湊在主執行緒上算（成本 10 一次約 90 ms），登入、註冊同時進來時，其他所有請求都要排隊。E 實測同時登入時打 `/health`：10 個同時登入 887 ms → 8 ms，40 個 3,231 ms → 6 ms。`bcrypt` 在背景執行緒算，不會卡住其他請求。
  - 原本擔心原生套件要編譯：`bcrypt@6` 的 npm 套件已經附上 Linux（glibc、musl）、Windows、macOS 的預先編譯檔，不用下載也不用編譯，npm 擋安裝腳本時也能用。
- **誰同意：** D 提出（PR AUTH-2），E 審查時建議改用 bcrypt@6，D 同意

### D-010 帳單遇到停用帳戶時回 `ACCOUNT_INACTIVE`

- **日期：** 2026/10/30
- **決定：**
  - 新增或修改帳單時指定停用的帳戶，回 409 `ACCOUNT_INACTIVE`（`details.field` 是 `accountId`）。修改時帳戶沒有變更就不檢查是否啟用。
  - 用停用的帳戶繳費、取消繳費，回 409 `ACCOUNT_INACTIVE`，請使用者先重新啟用帳戶。這兩個情況的扣款帳戶不是 body 的欄位，`details` 是 `[]`。
- **原因：**
  - PRD 15.11：停用的帳戶不能新增、刪除與它有關的交易。繳費會新增支出、取消繳費會刪除支出，所以兩個都要擋。
  - 新增、修改帳單時就擋下，使用者不會到繳費時才發現帳戶不能用。
- **誰同意：** E 提出（PR #21 的 Q2、Q15）；取消繳費要擋，C 已同意（C 的 `deleteBillTransaction` 照這個寫）；新增、修改帳單與 `details: []` 待 C 在 PR #47 確認
- **影響：** C 的 `AccountsService.assertAccountAndCategoryOwned` 用在新增、修改帳單；繳費、取消繳費由 C 的 `createBillTransaction`、`deleteBillTransaction` 檢查。

### D-E-002 貸款試算的期數改用 `paymentDay` 數還款日

- **日期：** 2026/11/04
- **決定：**
  - `GET /loans/payment-preview` 新增必填查詢參數 `paymentDay`（整數 1–31）。
  - 每月還款日 ＝ `paymentDay`，29–31 遇短月用當月最後一天。
  - 期數 n ＝ 台北今天（含）到 `endDate`（含）之間的還款日個數，至少 1。本月的還款日已過就從下個月算；今天剛好是還款日時算一期；晚於 `endDate` 的還款日不算。
  - `POST /loans` 沒帶 `monthlyPayment` 時的自動計算，用 body 的 `paymentDay`，規則相同。
  - PRD 15.8 的期數寫法「從本月到結清日所在月份（含頭尾）」改成上面的規則。
- **原因：**
  - 使用者填的未償餘額是繳完本月之後的數字。只看月份的話，本月還款日過後會多算一期，月付偏低（例如 每月 5 號還款，新增貸款日 10/6，1/5 結清：實際 3 期，原本算成 4 期）。
  - 用 `paymentDay` 而不是結清日的「日」：使用者想的是「每月幾號扣款」，Dashboard 的還款提醒也用 `paymentDay`，同一筆貸款只會有一個還款日。
  - 晚於結清日的還款日不算，跟 Dashboard 不列結清日之後的還款日一致。
- **沒有採用的方案：**
  - 照 PRD 原文，從本月算到結清月：上面「原因」第一點的問題。
- **誰同意：** E 提出，B 同意
- **影響：**
  - B：`LoanForm.vue` 試算帶 `paymentDay`、改繳款日時重新試算。
  - E：`LoanPaymentPreviewQueryDto` 加 `paymentDay`、Swagger description，`openapi.json` 在 LOAN-3／LOAN-4 的 PR 更新。修改 PRD 15.8 的期數寫法與第十三節試算的參數。

### D-E-001 `PATCH /loans/:id` 不自動重算每月還款，只有新增時自動算

- **日期：** 2026/11/03
- **決定：**
  - 只有 `POST /loans` 沒帶 `monthlyPayment` 時，後端用年利率自動算好存入（PRD 15.8）。
  - `PATCH /loans/:id` 沒帶 `monthlyPayment` 就保持原值，不管這次有沒有改未償餘額、年利率或結清日。
  - 使用者想改用新的建議值時，由前端呼叫 `GET /loans/payment-preview`，把建議值填進表單，跟其他欄位一起送出。
  - PRD 第十三節「`POST`／`PATCH` `/loans`：沒帶 `monthlyPayment` 時，後端用同一個公式自動算好存入」改成只有 `POST`。
- **原因：**
  - PRD 要使用者每月手動更新未償餘額，這種修改通常只帶餘額。如果 `PATCH` 沒帶月付就重算，使用者改成銀行實際扣款的月付（例如 18,500）每次都會被公式值（例如 17,969）蓋掉，**每個月更新餘額後都要再改一次月付**。只改名稱或備註也會觸發重算。
  - PRD 本身也把月付當成使用者確認過的長期設定：第十四節 `monthly_payment` 是「使用者確認後存入的值」，15.8 寫「之後不會因為利率變動自動更新」。
  - 和第十三節的 `PATCH` 通用規則「沒傳的欄位保持原值」一致；原本的寫法讓「沒帶月付」在 `PATCH` 有兩種解讀。
  - 前端 demo 的貸款表單（`frontend/app/components/LoanForm.vue`）已經是這個做法：修改既有貸款時不會自動覆蓋月付；餘額、年利率、結清日改變時重新試算，顯示建議月付，和目前的月付不同時提供「套用建議值」按鈕讓使用者自己決定要不要套用。
- **沒有採用的方案：**
  - 照 PRD 原文，`PATCH` 沒帶月付就重算：上面「原因」第一點的問題。
  - 請求帶了餘額、年利率或結清日，而且沒帶月付時才重算：每月更新餘額時一樣會蓋掉使用者填的月付。
- **誰同意：** E 提出，A B 同意
- **影響：**
  - E：修改 PRD 第十三節第 407 行。
  - B：修改貸款時一律帶上 `monthlyPayment`；想用新的建議值就用「套用建議值」。

### D-E-003 貸款改成已結清時不檢查未償餘額

- **日期：** 2026/11/04
- **決定：**
  - `status` 是 `closed` 時，後端不檢查 `outstandingBalance` 是不是 0，新增和修改都照存。
  - 已結清的貸款不管餘額多少，都不算進淨資產、Dashboard 的貸款摘要（未償餘額合計、還款日）和目標頁的 `activeLoanTotal`；這三個本來就只算 `active`（PRD 15.1）。
  - 後端也不自動把餘額改成 0：資料庫照存使用者填的值，只是不計算。
  - 前端顯示：
    - 貸款列表：已結清的貸款，未償餘額顯示 0 (跟計算一致) 或"已結清"。
    - 編輯表單：顯示資料庫裡的真實餘額，不顯示 0。
  - 不提示使用者把餘額改成 0。
- **原因：**
  - PRD 只規定「結清日已過時狀態必須是 `closed`」，沒有規定已結清的餘額。
  - 使用者常見的操作是只切狀態、忘了改餘額（例如還剩 320,000 時提前結清，或是轉貸到別家）。擋下來會讓使用者連「這筆不用再提醒」都存不了；餘額不影響任何計算，留著也不會算錯。
  - 餘額在所有計算裡都只算 `active`，已結清的餘額等於 0，手動改成 0 不會改變任何數字，只是多一個步驟；提示反而會讓使用者以為不改會出錯。所以不提示，由列表直接顯示 0 或"已結清"。
  - 編輯表單要顯示真實餘額，因為前端修改時送整份 body：表單顯示 0 的話，使用者只改備註按儲存，就會把 0 寫回資料庫，結果跟「後端自動改成 0」一樣。
- **沒有採用的方案：**
  - 已結清時餘額必須是 0，否則回 400：上面「原因」第二點的問題，還要多一個錯誤代碼。
  - 改成已結清時後端自動把餘額改成 0：
    - 誤觸後很難復原：小安誤按已結清，餘額 320,000 被改成 0；改回 `active` 時餘額是 0，她要記得原本的數字重填，沒發現的話淨資產會高估 320,000。存著不改的話，改回來 320,000 還在。
    - `balanceUpdatedAt` 會被刷新，45 天提醒也跟著重置，把「這個 0 是假的」藏起來。
    - 使用者沒有要求改的欄位被改掉，跟「沒傳的欄位保持原值」不一致。
  - 前端在狀態切成已結清時提示使用者順便把餘額改成 0 或"已結清"：上面「原因」第三點的問題。
- **誰同意：** E 提出，B 同意
- **影響：**
  - B：`pages/loans.vue:85` 的未償餘額，已結清的貸款顯示為"已結清"；`LoanForm.vue` 照舊顯示真實餘額，不加提示。前端 demo 目前可以存，只差列表的顯示。另外已結清的貸款會一併隱藏「餘額 xx 天前更新／該更新一下了」的提醒。

### D-E-004 修改貸款時，結清日或狀態有變更才檢查結清日已過

- **日期：** 2026/11/04
- **決定：**
  - `POST /loans`：不變，`status` 不是 `closed` 而且 `endDate` 早於台北今天，回 400 `LOAN_END_DATE_IN_PAST`。
  - `PATCH /loans/:id`：用原值合併請求後的值檢查同一條規則，但只有 `endDate` 或 `status` **跟原值不同**時才檢查。只改其他欄位（名稱、類型、餘額、月付、還款日、年利率、備註）不擋。
  - 比對的是值，不是請求有沒有帶這個欄位：前端整份送出時，`endDate` 寫同一天不算改。
  - 把 `closed` 改回 `active` 但結清日已過（US-L17），`status` 有變更，照樣擋。
  - 前端表單用同一條規則。
  - PRD 第十三節第 418 行（`endDate` 可以早於今天，但 `status` 必須是 `closed`）補上「修改時只在 `endDate` 或 `status` 有變更時檢查」。
- **原因：**
  - 結清日會隨時間自然過去。一筆 `active` 的貸款過了結清日、使用者還沒改成已結清時，原規則讓她連備註、未償餘額都改不了，錯誤訊息跟她要做的事無關。
  - 檢查應該只針對使用者這次改的東西。帳單也是同樣原則：扣款帳戶已停用時，只在帳戶有變更時檢查，改備註不受影響。
- **沒有採用的方案：**
  - 維持合併後一律檢查（逼使用者先結清）：上面「原因」第一點的問題。
  - 請求有帶 `endDate` 或 `status` 才檢查：前端修改時送整份 body，這兩個欄位每次都會帶，結果跟一律檢查一樣。
- **誰同意：** E 提出，B 同意
- **影響：**
  - B：`LoanForm.vue` 送出前的結清日檢查，修改時只在 `endDate` 或 `status` 跟原值不同才檢查。
  - E：LOAN-2 的 PATCH 照這條實作；`docs/error-codes.md` 的「何時發生」與 PATCH 的 Swagger 說明一起更新。修改 PRD 第十三節第 418 行。

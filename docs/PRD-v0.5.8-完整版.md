## 二、產品背景

很多人想存錢、想財富自由，但：

- 財務資料分散在不同帳戶、App、表格裡，不容易一眼掌握。
- 記帳很麻煩，欄位太多，三天就放棄。
- 收入、支出、貸款、帳單分開管理，容易忘記繳費。
- 「財富自由」聽起來很遠，不知道自己現在走到哪裡、下一步該做什麼。

這題的重點是：

- 看起來只是「記一筆帳」，其實餘額、淨資產、目標進度都要從同一份資料**即時算出來**，而且互相對得起來。
- 帳單繳費、取消繳費、自動產生下一期，必須在**同一個資料庫交易**裡完成，不能只成功一半。
- 使用者是 ADHD／懶人：**欄位越少越好、決定越少越好、一進來就知道下一步**。
- 所有推算都要標示「估計」，不能讓使用者誤以為是保證或投資建議。

## 三、產品目標

這個專案要完成一個可以 Demo 的個人財務服務：

- 使用者用 Email＋密碼註冊，**30 秒、點 2–3 下**完成財富自由問卷，立刻看到目標與第一站進度。
- 使用者可以管理帳戶（現金、銀行、投資、信用卡），餘額由系統計算。
- 使用者可以**快速記帳**：只填金額＋點分類就能存。
- 使用者可以記錄貸款、帳單；帳單繳費自動產生支出與下一期。
- Dashboard 顯示淨資產、本月收支、近期帳單、目標進度，以及**一句「現在最該做什麼」**。
- 所有數字由後端計算，重新整理、重新登入後資料仍在。
- 小組能說清楚使用哪些 AI 服務加速開發，以及自己做了哪些判斷。

### 核心設計原則

> **不要要求使用者變得更自律，而是讓系統更容易使用。**
> 這也適合沒有 ADHD 的人：每個人都希望少花時間處理繁瑣的財務工作。

| 原則 | 做法 | 在哪裡落實 |
|---|---|---|
| 少輸入 | 預設值、自動帶入、按鈕／下拉選單，不重複填寫 | 問卷預選、快速記帳、貸款月付自動算、財富自由年齡自動算 |
| 快速記帳 | 2 次操作內完成一筆交易 | FR-09、第十二節 |
| 任務拆小 | 一次只呈現最重要的一件事，不同時塞滿資訊 | Dashboard 一句下一步（15.5） |
| 提醒而非責備 | 清楚提示到期帳單，附上「直接去繳」的按鈕；文字不用「你又超支了」這類語氣 | 15.5、帳單頁 |
| 降低記憶負擔 | 系統主動追蹤未繳帳單、貸款餘額更新日、14 天資金缺口 | 15.5、貸款頁 |
| 允許中斷 | 表單未送出的內容暫存在瀏覽器（不含密碼），下次打開還在；不要求一次填完 | 快速記帳、帳戶與帳單表單 |
| AI 輔助但不依賴 AI | 先用簡單、可靠的規則自動化；AI 辨識單據等列為未來版本 | 第五節非目標 |

**首頁（Dashboard）優先回答 3 個問題，而不是先列一堆報表：**

1. 今天有什麼帳單要處理？（逾期＋今天到期）
2. 這個月的錢夠不夠用？（14 天資金缺口）
3. 我現在只需要做哪一件事？（一句下一步）

## 五、非目標

這些事情不是本次的重點。除非 P0 全部通過，否則不要做。

- 不串接銀行、信用卡、券商、加密貨幣交易所、股價 API。
- 不做 AI 理財建議、AI 自動分類、OCR 收據辨識。
- 不做正式會計、報稅、薪資、多人協作。
- 不做投資組合分析、買賣建議、保證性的財務預測；所有推算都標示「估計」。
- 不做多幣別與匯率；只用新台幣（TWD），`currency` 欄位只預留、不開放輸入。
- 不做個人／公司標籤與公司帳務。
- 不做多個目標；每位使用者只有一個財務目標。
- 不做貸款還款表、本金與利息拆分，也不在還款後自動扣減貸款餘額；貸款餘額由使用者手動更新。月付只在新增或修改貸款時，依本息平均攤還算一次建議值（15.8）。
- 不做 Email、手機推播通知；只做站內提示。
- 不做信用卡帳單週期、最低應繳、循環利息。
- 不做預算功能（P1 之後再評估）。

## 六、核心產品問題

很多人會直覺覺得：

> 記帳不就是輸入一筆金額，然後加總嗎？

這題的重點是讓你們理解，真正的產品流程比較像這樣：

```txt
註冊 → 2 題問卷
  ↓
系統算出目標（每月花費 × 300）並建立「現有資產（估計）」帳戶
  ↓
使用者快速記帳／繳帳單／新增真實帳戶
  ↓
後端即時計算：帳戶餘額 → 帳戶合計 → 淨資產 → 目標進度 → 里程碑
  ↓
規則判斷「一句下一步」：逾期帳單 → 資金缺口 → 下一站
  ↓
Dashboard 顯示：一個大數字＋一句下一步
```

你們不是只做幾張表單，而是做一套**同一份資料、到處都算得一樣**的帳務核心。

## 七、角色與權限

| 角色 | 可以做什麼 | 不能做什麼 |
|---|---|---|
| 訪客 | 註冊、登入 | 不能呼叫任何業務 API（回 401） |
| 已登入、未完成問卷 | 填問卷、呼叫 `/auth/me` | 前端一律導向問卷頁 |
| 使用者 | 管理自己的帳戶、交易、貸款、帳單、目標；查看 Dashboard | 不能讀取或修改他人資料（回 404，不洩漏資料是否存在） |

做法：

- 自建 JWT（`@nestjs/jwt`＋Passport），密碼 bcrypt 雜湊。
- token 有效期 24 小時，不做 refresh token（避免 Demo 中途被登出）。
- Email 一律轉小寫後儲存與比對。

## 八、目標使用者與情境

| 使用者 | 需求／情境 |
|---|---|
| ADHD／懶得記帳的人 | 欄位一多就放棄；需要一打開就知道下一步 |
| 想財富自由的上班族 | 想知道「我要存多少、現在走到哪、還差多少」 |
| 有多個帳戶的人 | 現金、銀行、投資、信用卡分開，但想看合計與淨資產 |
| 有貸款或固定帳單的人 | 怕忘記繳費，想知道 14 天內的錢夠不夠付 |

核心任務：

> 我不想花時間記帳，但想知道自己離財富自由還有多遠，以及現在最該做哪一件事。

目前沒有真實使用者。第一週由 A 找 3–5 位組外的人看線框圖，確認問卷 30 秒內填得完。

## 十、MVP 範圍

MVP 基準版請先固定成：

> 註冊 → 30 秒問卷 → 看到目標與第一站 → 新增帳戶 → 快速記帳 → 新增帳單並繳費 → Dashboard 顯示淨資產、本月收支、近期帳單、目標進度與一句下一步。

| # | 功能 | 說明 |
|---|---|---|
| 1 | 登入 | Email＋密碼註冊、登入、JWT、次數限制 |
| 2 | 財富自由問卷 | 2 題問卷，建立目標與「現有資產（估計）」帳戶 |
| 3 | 帳戶管理 | 新增、列表、修改、停用；餘額即時計算 |
| 4 | 交易管理 | 收入、支出、轉帳 CRUD；篩選與分頁 |
| 5 | 快速記帳 | 金額＋分類即可儲存 |
| 6 | 貸款管理 | 貸款 CRUD，手動更新未償餘額 |
| 7 | 帳單管理 | 帳單 CRUD、繳費、取消繳費、停止重複 |
| 8 | 財務目標 | 目標金額、進度百分比、里程碑 |
| 9 | Dashboard | 淨資產、本月收支、近期帳單、目標進度、一句下一步 |
| 10 | 資料持久化 | 重新整理、重新登入後資料仍在 |

**範圍原則：** 先確保帳戶、交易、帳單的數字正確，再做目標與 Dashboard；P0 全部通過驗收後才開始 P1。進度落後時先砍 P1，不砍測試。

## 十一、功能規格

| ID | 功能 | 規格 | 優先級 |
|---|---|---|---|
| FR-01 | 服務狀態檢查 | `GET /health` 回傳服務與資料庫是否正常 | Must |
| FR-02 | 註冊與登入 | Email 小寫、密碼 ≥ 8 碼、bcrypt、JWT 24 小時 | Must |
| FR-03 | 登入次數限制 | 每個 IP 每分鐘 10 次；每個 Email 每 15 分鐘失敗 5 次；測試環境用環境變數調高 | Must |
| FR-04 | 問卷 | 2 題、Q1 必填、Q2 可跳過；同一個資料庫交易內建立目標與估計帳戶；重送回 409 | Must |
| FR-05 | 帳戶 CRUD | 四種類型；只有信用卡初始餘額可為負；有交易只能停用 | Must |
| FR-06 | 帳戶停用 | 餘額必須為 0，且沒有未來日期的交易 | Must |
| FR-07 | 估計帳戶轉換 | 新增真實帳戶時詢問是否從估計值扣掉（上限＝估計帳戶目前餘額），扣到 0 自動停用；刪除真實帳戶時可加回（15.9） | Must |
| FR-08 | 交易 CRUD | 金額 > 0；收入／支出要有對應分類；轉帳沒有分類、兩個帳戶不同 | Must |
| FR-09 | 快速記帳 | 必填：金額、分類；帳戶預設上次使用；日期預設今天 | Must |
| FR-10 | 繳卡費 | 按鈕建立銀行 → 信用卡的轉帳，不是支出 | Must |
| FR-11 | 交易列表 | 依日期、類型、分類、帳戶篩選；分頁 20 筆、上限 100 | Must |
| FR-12 | 系統分類 | seed 建立 12 個系統分類，`code` 唯一，可重複執行 | Must |
| FR-13 | 貸款 CRUD | 狀態 `active`／`closed`；記錄 `balance_updated_at` | Must |
| FR-14 | 帳單 CRUD | 只能用支出分類；扣款帳戶必須啟用 | Must |
| FR-15 | 帳單繳費 | 原子操作；預定金額與實繳金額分開；防重複繳費 | Must |
| FR-16 | 取消繳費 | 刪除本期支出；下一期待繳就一起刪，已繳則回 409 | Must |
| FR-17 | 停止重複 | 修改系列最新一張待繳帳單的 `recurrence` | Must |
| FR-18 | 目標與里程碑 | 目標＝每月花費 × 300；里程碑依第十五節規則 | Must |
| FR-19 | Dashboard | 一支 API 回傳所有區塊與一句下一步 | Must |
| FR-20 | 推算達成日 | 依平均每月儲蓄推算 | Should（P1） |
| FR-21 | 月收支趨勢 | 最近 6 個月長條圖 | Should（P1） |
| FR-22 | 短期現金流預警 | 未來 60 天餘額推算 | Should（P1） |
| FR-23 | 餘額調整交易 | 不計入收支 | Should（P1） |
| FR-24 | 刪除後復原 | 5 秒 Undo | Could（P1） |

## 十二、使用者流程

### 註冊與問卷流程

```txt
打開網站 → 註冊（Email＋密碼）
  ↓

  → 按鈕：3萬／4萬（預選）／5萬／8萬／自己填（1,000–333,000）

  → 按鈕：0／10萬／50萬／100萬／自己填（0–1億）
  ↓
送出（同一個資料庫交易）：建立 goals＋「現有資產（估計）」帳戶
  ↓
結果頁：目標 1,200 萬＋「再存 X 元就到第 1 站！」→ 開始記帳
```

```txt
打開 Dashboard → 按「＋」
  ↓
輸入金額 → 點分類（常用的排前面）
  ↓
（日期＝今天、帳戶＝上次使用，都可以改，收在「更多」）
  ↓
儲存 → Dashboard 數字立刻更新
```

```txt

  ↓
按「繳費」→ 預填金額（預定金額）、日期（今天），可修改

  ↓
帳戶餘額、Dashboard 即時更新
```

### 新增真實帳戶流程

```txt
帳戶頁 → 新增「台新銀行，100,000」
  ↓

  ↓
是 → 估計帳戶 500,000 → 400,000（合計不變）

```

## 十五、計算規則

這一節是全組共用的計算定義，**任何模組都不能自己另外定義**。「今天」一律用 Asia/Taipei 計算（產品決策），由共用的 `ClockService` 提供。

### 15.1 共用計算結果（唯一的計算服務）

所有數字由 C 負責的 **`FinanceCalcService`** 提供，其他模組（goals、dashboard、FIRE、bills）一律呼叫它，**不得自己重寫公式**。

| 計算結果 | 公式 | 未來日期交易 | 停用帳戶 | 估計帳戶 | 扣貸款 | 用在哪裡 |
|---|---|---|---|---|---|---|
| 帳戶目前餘額 | 初始餘額＋收入−支出＋轉入−轉出 | 不算 | — | — | 否 | 帳戶頁 |
| 帳戶合計 | 啟用帳戶目前餘額加總（含信用卡負值、含投資） | 不算 | 不算 | **算** | 否 | 目標進度、FIRE 現在資產 |
| 淨資產 | 所有帳戶目前餘額 − `active` 貸款未償餘額 | 不算 | 算（餘額必為 0） | **算** | **是** | Dashboard 財務概況 |
| 可用現金 | 啟用中 `cash`＋`bank` 帳戶目前餘額 | 不算 | 不算 | **不算** | 否 | 14 天資金缺口（15.5） |
| 本月收支 | 該月收入合計、支出合計 | 不算 | 算 | — | 否 | Dashboard |
| 預計現金流（P1） | 可用現金＋未來交易＋待繳帳單 | **算** | 不算 | 不算 | 否 | 現金流預警 |

- 估計帳戶算進「帳戶合計」和「淨資產」（它代表使用者說他有的錢），但**不算進可用現金**（不知道是不是能馬上動用的存款）。

### 15.2 收支與儲蓄率

- 收入合計只加 `income`，支出合計只加 `expense`。
- **不算收支的：** 轉帳、繳卡費（＝轉帳）、餘額調整（P1）。
- **貸款還款整筆算支出**（MVP 不拆本金與利息）。
- 儲蓄率 ＝（收入 − 支出）÷ 收入 × 100，小數一位；收入為 0 時回 `null`（畫面顯示「—」）；可為負。
- 四捨五入只在最後一步做。

### 15.3 財務目標

- 目標金額 ＝ 每月花費 × 300（4% 提領率，即 × 12 ÷ 4%）。例：每月 4 萬 → 1,200 萬。
- 目前金額 ＝ 帳戶合計（15.1）。
- 達成百分比 ＝ 目前金額 ÷ 目標金額，四捨五入到小數一位；≤ 0 顯示 0%；≥ 目標顯示 100% 與「已達成」。
- 通膨提示（只顯示，不改計算）：假設年通膨 2%，20 年後每月 4 萬 ≈ 5.9 萬（4 萬 × 1.02²⁰）。
- 目標頁固定標示：「目標進度依啟用帳戶合計計算，包含投資帳戶和信用卡欠款，不扣除另外記錄的貸款。這個數字不等於淨資產，也不等於馬上能用的現金。本結果為估算，非投資建議。」

### 15.4 里程碑

1. 候選站：10 萬（緊急預備金）、100 萬（第一桶金）、目標 ÷ 2（一半）。
2. 由小到大排序，刪掉 ≥ 目標的站，重複的只留一個。
3. 最後加上終點（財富自由＝目標金額）。

例：每月 5,000 → 目標 150 萬 → 10 萬 → 75 萬 → 100 萬 → 150 萬。

畫面主數字顯示「再存 X 元就到第 N 站」，總百分比放小字（避免一直卡在 0.x%）。

### 15.5 一句下一步（Dashboard）

依序判斷，第一個符合的就顯示：

| 順序 | 條件 | 顯示 |
|---|---|---|
| 1 | 有逾期、未繳的帳單 | 「有 N 張帳單逾期」 |
| 2 | 有啟用的現金／銀行帳戶，且 14 天內有待繳帳單，且缺口 X > 0 | 「未來 14 天的已知帳單，整體資金**可能**不足，差 X 元」 |
| 3 | 有目標 | 「再存 X 元就到第 N 站」 |
| 4 | 沒有目標 | 「先完成 30 秒問卷」 |

- 缺口 X ＝ `due_date` 在**今天到今天＋14 天（含頭尾）**的待繳帳單 `amount` 合計 − 可用現金（15.1）。
- **已逾期的帳單不算進缺口**（第 1 條已經單獨提醒）；不含投資、信用卡、估計帳戶、未來交易、預計收入。
- 「今天」由 `ClockService` 提供（Asia/Taipei）。
- 只說「整體資金」，因為錢可能在別的帳戶，不能保證每張帳單的扣款帳戶都夠。
- P1 現金流預警完成後，第 2 條改用預計現金流。

### 15.6 P1：推算達成日

- 每月儲蓄 ＝ 每月收入 − 每月支出。
- 有 3 個以上完整日曆月（不含本月、不含未來交易）時，用**最近最多 6 個**完整月份的平均；不足 3 個月時用自估值；自估值也沒有 → 顯示「資料不足，請填每月收支自估」，不當成 0。
- 所需月數 ＝（目標 − 目前）÷ 每月儲蓄，無條件進位；儲蓄 ≤ 0 → 「以目前收支無法達成」；> 600 個月 → 「以目前速度超過 50 年」。
- 固定標示「依目前儲蓄速度估算，未計入投資報酬」。

### 15.7 財富自由年齡（P0，顯示在目標頁，懶人不用輸入）

**不做獨立試算頁**，目標頁直接多一行：「照現在的速度，你可以在 **X 歲**財富自由」，下面小字列出用了哪些假設。

**自動帶入的資料：**

| 欄位 | 自動帶入來源 | 沒有資料時 |
|---|---|---|
| 年支出 | 問卷的每月花費 × 12 | — （問卷必填，一定有） |
| 年儲蓄 | 有 3 個以上完整月：最近最多 6 個完整月的平均（收入 − 支出）× 12 | 用 `est_monthly_saving` × 12；也沒有 → 目標頁問 1 次「每月大概能存多少？」 |
| 現在資產 | 帳戶合計（15.1），**未扣除貸款** | 0 |
| 年齡 | 今年 − `birth_year` | 目標頁問 1 次「你是哪一年出生的？」（選填，存起來） |
| 提領率 | 固定 4% | — |
| 投資報酬率 | 固定 6% | — |
| 通膨率 | 固定 2% | — |

P0 假設值固定、不做滑桿；缺資料時不顯示年齡，改顯示「補上出生年，就能算出你幾歲財富自由」這類一句提示。

**計算（全部用今日幣值）：**

- 實質報酬率 ＝（1 ＋ 報酬率）÷（1 ＋ 通膨率）− 1。例：6%、2% → 3.92%。
- FIRE 目標 ＝ 年支出 ÷ 提領率（提領率 4% 時就是 × 25，等於每月花費 × 300，跟問卷目標一致）。
- 逐年模擬：年底資產 ＝ 年初資產 ×（1 ＋ 實質報酬率）＋ 年儲蓄。**年儲蓄在每年年底一次投入**（第一年的年儲蓄不賺當年報酬）。第一次 ≥ FIRE 目標的那一年，就是財富自由年齡（＝ 現在年齡 ＋ 經過年數）。
- 中間計算保留完整精度，只在顯示時四捨五入；測試要固定驗算案例**和每一年的資產**，不只驗最後年齡。
- 邊界：已達成 →「你已經財富自由了」；年儲蓄 ≤ 0 且資產報酬不夠 →「以目前收支無法達成」；超過 100 歲 →「100 歲前無法達成」。
- 畫面：只顯示一句結論＋假設小字（不畫曲線）。
- 固定標示「本結果為依假設試算，非投資建議」。
- 有 `active` 貸款時，小字顯示「目前資產未扣除貸款 X 元」（跟目標進度同一個口徑）。

**驗算案例：** 40 歲、提領率 4%、年支出 600,000、年儲蓄 600,000、現在資產 5,000,000、報酬率 6%、通膨 2% → 實質 3.92%、FIRE 目標 15,000,000 → **51 歲**。

> 注意：網路上有些 FIRE 計算機用「名目報酬＋支出每年漲通膨、儲蓄不漲」，同一組數字會算出 52 歲。我們用今日幣值，是為了跟問卷目標（每月花費 × 300）用同一個基準；簡報可以說明這個取捨。
> P2 的退休試算（三情境、退休金、貸款結清、可調整假設的試算頁）在這個基礎上擴充，不另外做一套。

### 15.8 貸款月付自動計算（P0，嵌在貸款表單裡）

**不做獨立試算頁。** 使用者新增／修改貸款時，填「未償餘額」「年利率」「結清日」，系統就自動填好「每月還款」，並在旁邊顯示「預估總利息 X 元」。使用者可以改成銀行實際的金額；沒填年利率時不自動算，請使用者自己填每月還款。

**本息平均攤還：**

- 月利率 r ＝ 年利率 ÷ 12；剩餘期數 n ＝ 從本月到結清日所在月份的月數（含頭尾），至少 1。
- 每月還款 ＝ 貸款金額 × r ÷（1 −（1 ＋ r）⁻ⁿ）；年利率 0% 時 ＝ 金額 ÷ n。
- 後端內部仍逐期計算（用來得到總利息），但**畫面不顯示還款表**。
- **取整規則：** 中間計算用 `Decimal` 保留完整精度；每期月付與每期利息四捨五入到元；**最後一期**＝剩餘本金＋最後一期利息（吸收累積尾差），保證剩餘本金剛好為 0。
- 總利息 ＝ 逐期利息加總。
- 不做：分段利率、寬限期、利息比較（列為未來版本）。

**驗算案例：** 1,000,000 元、5 年、年利率 3% → 未取整月付 17,968.69 元；還款表第 1–59 期每月 17,969 元、第 60 期 17,949 元；**總利息 78,120 元**（不取整的公式值為 78,121.44 元）。

**限制：** 自動算出的月付只是建議值，存入前使用者可以修改；之後不會因為利率變動自動更新。

### 15.9 估計帳戶轉換

- 新增真實帳戶（初始餘額 X）時詢問：「要從『現有資產（估計）』扣掉嗎？」
- 實際扣除金額 ＝ min（X，估計帳戶**目前餘額**），不會讓估計帳戶變成負數；X ≤ 0（例如信用卡）時不詢問。
- 做法：估計帳戶的 `opening_balance` 減去扣除金額（估計帳戶就算有交易也能正確反映）；新帳戶的 `deducted_from_estimate` 記錄扣了多少。
- **新增帳戶與扣除在同一個資料庫交易內完成**；新增失敗時估計帳戶不會被單獨扣除。
- 估計帳戶目前餘額扣到 0 時自動停用。
- 刪除真實帳戶（只有沒有交易時才能刪）時，若 `deducted_from_estimate` 有值，詢問「要把 X 加回估計值嗎？」（預設是），同一個資料庫交易內加回；估計帳戶已停用就重新啟用。
- 停用真實帳戶（餘額必須為 0）不會加回估計值。
- 扣除與加回後，帳戶合計不變，目標進度不會突然增加。

### 15.10 信用卡

- 刷卡消費 ＝ 信用卡帳戶的 `expense`（餘額變更負）。
- 繳卡費 ＝ 銀行 → 信用卡的 `transfer`，**金額由使用者填**，預設為目前欠款。
- 部分繳款：例如刷 30,000、繳 20,000 → 信用卡餘額 −10,000（仍欠 10,000），不算結清。
- 超額繳款：信用卡餘額可以變成正數（溢繳），系統不阻擋，帳戶頁顯示「溢繳 X 元」。
- 退款：P0 不做專用功能；請修改或刪除原本那筆支出。
- 繳卡費不再計入支出；同一筆消費只算一次。

### 15.11 帳戶與交易的限制

- `opening_balance` 可以修改（用來修正輸入錯誤），修改後目前餘額跟著變動；**停用帳戶不能修改**。
- 停用的帳戶：不能新增、修改、刪除與它有關的交易（轉出或轉入任一方），也不能把交易移進或移出它；要改請先重新啟用。
- 交易日期可以改成未來日期（帳戶必須是啟用的）；改了之後依 15.1 不計入目前餘額。
- 停用條件：目前餘額為 0，而且沒有未來日期的交易。

### 15.12 P1：餘額調整（`adjustment`）草案

- P0 **不實作**，`transaction_type` enum 也不先加。
- P1 草案：新增 `adjustment` 類型＋`adjustment_direction`（`increase`／`decrease`），`amount` 仍 > 0。
- 餘額公式變成：初始餘額＋收入−支出＋轉入−轉出＋調增−調減。
- 不計入收入、支出、儲蓄率；只能用在 `investment` 帳戶（P1 開始前再確認）。

## 十六、帳單與資料流程

### 16.1 繳費（`POST /bills/:id/pay`）

同一個資料庫交易內：

```txt
鎖定這個系列的所有帳單（SELECT ... WHERE series_id = ? FOR UPDATE）
→ 確認這張 status = pending，否則 409
  ↓
確認扣款帳戶是啟用的，否則 409
  ↓
用 paid_amount／paid_date 建立支出交易（bill_id 唯一）
  ↓
帳單改成 paid，寫入 paid_amount、paid_date
  ↓
若 recurrence ≠ none：建立下一期（同一個 series_id、amount 沿用本期預定金額、
due_date 依 due_day／due_month 推算）
  ↓
全部成功才提交；任何一步失敗全部復原
```

- `paid_amount` 預設＝`amount`，`paid_date` 預設＝今天，都可以改；`paid_date` 不可晚於今天。
- 前端按下後鎖住按鈕，但**後端才是真正的防護**。

### 16.2 取消繳費（`POST /bills/:id/unpay`）

- 同樣先鎖定整個系列。
- 只能取消**系列中最後一張已繳**的帳單：之後那一期還是 `pending` → 一起刪掉；之後那一期已繳 → 回 409（請先取消下一期）。
- 刪除本期的支出交易，帳單改回 `pending`，清空 `paid_amount`、`paid_date`。
- 取消後再繳一次，會重新產生下一期（因為舊的下一期已經刪掉）。

### 16.3 停止重複（`POST /bills/:id/stop-recurrence`）

- 一個系列同時最多只有 1 張待繳（下一期只在繳費時產生，資料庫部分唯一索引保證）。
- 不論從系列中的哪一張（包含歷史已繳的）進入，後端都用 `series_id` 找到**最新那張待繳帳單**，把它的 `recurrence` 改成 `none`。這張繳費後就不會再產生下一期，整個系列停止。
- 系列中沒有待繳帳單時（例如最新一期已被刪除），回 200，不做任何事。
- `keepCurrent: true` → 保留這張（這期還要繳）；`false` → 刪掉這張。
- 已繳的歷史帳單都不動。

### 16.4 月底日期

- 下一期依 `due_day` 推算；短月改成當月最後一天，下一期再回到原本的日期。
- 例：1/31 → 2/28（閏年 2/29）→ 3/31。
- 年度帳單依 `due_month`＋`due_day`：2/29 的年度帳單，非閏年改成 2/28，閏年回到 2/29。

### 16.5 帳單其他規則

- 已繳的帳單不能直接刪除，要先取消繳費。
- 刪除待繳帳單：只刪這一張；因為它就是系列最新一期，刪除後系列不會再產生下一期（等於停止重複），歷史已繳帳單保留。
- 由帳單產生的交易不能在交易頁修改或刪除（回 409）。
- 逾期不另存狀態，由「待繳且到期日 < 今天」計算。

### 16.6 帳單狀態轉換表

| 操作 | 允許的來源狀態 | 資料庫結果 | 錯誤 |
|---|---|---|---|
| 新增 | — | 新帳單 `pending`，產生新的 `series_id` | 400（驗證失敗） |
| 修改 | `pending` | 更新欄位；`paid` 的帳單只能改名稱與備註 | 409 `BILL_ALREADY_PAID` |
| 繳費 | `pending` | 建立支出、改 `paid`、重複帳單產生下一期 | 409 `BILL_ALREADY_PAID`、409 `ACCOUNT_INACTIVE` |
| 取消繳費 | `paid`，且之後那一期不是 `paid` | 刪除支出、改 `pending`、刪除之後的待繳期 | 409 `NEXT_BILL_ALREADY_PAID` |
| 停止重複 | 系列中任一張 | 最新待繳那張 `recurrence = none`（可選刪除） | — |
| 刪除 | `pending` | 刪除這一張 | 409 `BILL_ALREADY_PAID` |
| 同時兩個請求 | — | 先鎖定整個系列，後到的請求看到新狀態再判斷 | 依上面規則 |

## 十七、前台畫面需求

需要有前台畫面可以操作，不只提供 API。所有畫面在常見手機寬度下可操作。

### 問卷頁

- 2 題、大按鈕、預選 4 萬
- Q2 有「跳過」
- 結果頁：目標金額＋第一站進度＋「開始記帳」按鈕

### Dashboard

- 第一屏依序回答 3 個問題（核心設計原則）：
  1. **今天有什麼帳單要處理？**（逾期＋今天到期，附「去繳費」按鈕）
  2. **這個月的錢夠不夠用？**（14 天資金缺口，夠的話顯示「✓ 14 天內的帳單付得出來」）
  3. **我現在只需要做哪一件事？**（一句下一步＋1 個大數字）
- 往下滑才是報表：本月收入、支出、儲蓄率
- 帳戶合計與淨資產**分開標示**
- 14 天內與逾期帳單（各最多 5 筆）
- 貸款摘要：未償餘額合計；**未來 14 天內的還款日**（和帳單同一個 14 天範圍）
- 還沒完成的區塊顯示「準備中」（API 的 `unavailable`），方便分階段交付
- 右下角「＋」快速記帳

### 快速記帳

- 金額輸入（數字鍵盤）
- 分類按鈕（常用的排前面、記住上次的）
- 「更多」：日期、帳戶、備註
- 沒有可用帳戶時，先引導建立或選擇帳戶
- 轉帳、繳卡費用獨立按鈕

### 帳戶頁

- 帳戶列表與目前餘額；估計帳戶標示「估計」
- 有交易的帳戶（`hasTransactions: true`）只顯示「停用」，沒有交易才顯示「刪除」
- 新增帳戶時詢問是否從估計值扣掉

### 交易頁

- 列表、篩選、分頁；帳單產生的交易（`isBillGenerated: true`）隱藏修改／刪除

### 貸款頁

- 未償餘額、每月還款、繳款日、「餘額最後更新：X 天前」（超過 45 天提醒）
- 標示「還款不會自動扣未償餘額，請每月手動更新」
- 新增／修改表單：填完未償餘額、年利率、結清日後，「每月還款」自動填好（可改），旁邊顯示預估總利息

### 帳單頁

- 待繳、已繳、逾期；繳費、取消繳費、停止重複按鈕

### 目標頁

- 目標金額、目前金額、還差多少、百分比、進度條、里程碑
- 通膨小字提示與免責說明（15.3）
- 一句「照現在的速度，你可以在 X 歲財富自由」＋假設小字；缺出生年或儲蓄資料時，只問那 1 題（15.7）

## 十八、錯誤處理與邊界情境

| 情境 | 預期處理 |
|---|---|
| 未登入或 token 過期 | 401，前端導回登入 |
| 存取他人資料 | 404，不洩漏資料是否存在 |
| 金額空白、0、負數、非數字 | 400，顯示可理解的錯誤 |
| 非信用卡初始餘額為負 | 400 `OPENING_BALANCE_NEGATIVE` |
| 轉帳轉給同一個帳戶 | 400 `TRANSFER_SAME_ACCOUNT` |
| 停用有餘額或有未來交易的帳戶 | 409 |
| 新增／修改／刪除與停用帳戶有關的交易 | 409 `ACCOUNT_INACTIVE`，請先重新啟用帳戶 |
| 修改停用帳戶的初始餘額 | 409 `ACCOUNT_INACTIVE` |
| 請求內容引用別人的帳戶或分類 | 400 `ACCOUNT_NOT_FOUND`／`CATEGORY_NOT_FOUND`（不洩漏是否存在） |
| 路徑上的帳單、交易、帳戶找不到或屬於他人 | 404 `BILL_NOT_FOUND`／`TRANSACTION_NOT_FOUND`／`ACCOUNT_NOT_FOUND` |
| 修改已繳帳單的金額或日期 | 409 `BILL_ALREADY_PAID` |
| 刪除有交易或被帳單使用的帳戶 | 409，提示改用停用 |
| 問卷重送 | 409 `ONBOARDING_ALREADY_DONE` |
| 帳單連點兩次繳費 | 第二次 409 `BILL_ALREADY_PAID`，只有一筆支出 |
| 用停用帳戶繳費 | 409 |
| 取消繳費但下一期已繳 | 409 `NEXT_BILL_ALREADY_PAID` |
| 實繳日期晚於今天 | 400 `PAID_DATE_IN_FUTURE` |
| 修改／刪除帳單產生的交易 | 409 `BILL_LINKED_TRANSACTION` |
| 收入為 0 | 儲蓄率顯示「—」 |
| 沒有現金／銀行帳戶 | 不計算資金缺口 |
| 資料庫寫入失敗 | 500，全部復原，不可假裝成功 |
| 任一 Dashboard service 出錯 | 整支回 500，不回傳部分數字 |

## 十九、技術限制與建議套件

### 前端

| 類型 | 建議 |
|---|---|
| Framework | Nuxt＋Tailwind CSS（TypeScript） |
| 圖表 | 待定（P1 才需要，開始做趨勢圖前再選） |
| API 型別 | `openapi-typescript` 從 Swagger JSON 產生 |

### 後端

| 類型 | 選擇 |
|---|---|
| Web framework | NestJS（TypeScript） |
| ORM／Migration | Prisma；本機 `migrate dev`，部署只跑 `migrate deploy` |
| Database | PostgreSQL 16（本機 Docker：`app_dev`、`app_test`） |
| 登入 | `@nestjs/jwt`＋Passport、bcrypt、`@nestjs/throttler` |
| Validation | class-validator＋DTO |
| API 文件 | `@nestjs/swagger`，掛在 `/api/docs` |
| 日誌 | `nestjs-pino`，JSON 到 stdout，每個請求有 request ID |
| 測試 | Jest＋Supertest（連真實 PostgreSQL）、Playwright |
| CI | GitHub Actions：lint、型別檢查、測試、migration 從空資料庫跑一次；用 PostgreSQL 16 service container 跑整合測試（`test:e2e`）；全域設定抽成 `configureApp(app)`，正式程式與測試共用 |

### 限制

- 只用標準 PostgreSQL 功能，一律經由 Prisma；不使用 Supabase 的登入、資料列權限或前端 SDK。
- Prisma 寫不出來的 CHECK 約束，在 migration SQL 手動加。
- 機密只放環境變數，`.env` 不進版控。
- 後端從第一週就有 Dockerfile。
- 部署平台會從 Vercel＋Render＋Supabase 換到 AWS（第二十九節第 4 項），程式不可綁定平台：
  - Nuxt 的 Nitro preset 以環境變數切換（Vercel 用 `vercel`，EC2 用 `node-server`）。
  - 資料庫連線字串只從環境變數讀取。使用 Supabase 時，Prisma 設定兩組連線字串：一般查詢走連線池，migration 走直連。
  - 日誌只寫到 stdout，不寫檔案。
- 密碼、token、完整請求 body 不寫入日誌。

### 登入與安全

- **Token：** 後端回傳 access token，前端用 `Authorization: Bearer` 帶入；存在 `localStorage`（重新整理後仍登入），登出時清除。不使用 Cookie，所以不需要 CSRF token。
- **XSS 防護（因為 token 在 `localStorage`）：** 不使用 `v-html`；使用者輸入一律當文字顯示；設定基本 Content-Security-Policy。
- **登入次數限制：** `@nestjs/throttler` 預設存在記憶體。MVP **只部署單一後端實例**，這個限制有效；若之後要多實例，改用共享儲存（例如 Redis）。這項限制寫進 README。

### Schema 與 migration 的責任

- **D 是 schema 與 migration 的唯一審查入口**；C、E 可以在自己的 PR 改自己模組的資料表，但必須 D 核准才能合併。
- 手動加的 SQL（CHECK、部分唯一索引）寫在 migration 檔裡，跟著 migration 進版控，不另外手動執行。
- CI：每個 PR 都從空資料庫跑完全部 migration；並用 `prisma migrate diff` 檢查 schema 與 migration 是否一致（不一致就失敗）。
- 合併前先同步 `main`；期間若有其他 migration 合併，要重新產生自己的 migration。

## 二十三、風險與取捨

| 風險 | 可能影響 | 建議取捨 |
|---|---|---|
| 問卷估計資產與真實帳戶重複 | 目標進度灌水 | `is_estimate`＋每次新增都詢問扣掉 |

| 貸款餘額過期 | 淨資產偏低 | 顯示最後更新日，45 天提醒 |
| 未來交易提早計入 | 餘額、目標提早變動 | 只有日期 ≤ 今天才計入 |
| 各模組各自算數字 | Dashboard 對不起來 | 第十五節是唯一的計算定義 |
| 推算被當成財務建議 | 使用者誤會 | 固定標示「估算，非投資建議」 |
| NestJS 與部署學習成本 | 進度落後 | 第一週全組跑同一份入門範例；第一週完成第一次部署 |
| 前後端串接太晚 | 最後一週才整合 | 第一週完成 Swagger 空殼；11/01 前最小流程上線 |
| C 的 service 太晚 | D、E 被卡住 | C 的 service 11/08 前完成 |
| A 工作太多 | 前端卡住 | B 承接共用元件與 Dashboard 報表區塊；P1 頁面 11/22 再分配 |
| D 工作太多 | 資料庫與登入卡住 | auth 由 E 寫整合測試；財富自由年齡只做純函式＋一行顯示，不做試算頁 |
| P1 範圍太大 | 犧牲 P0 測試 | P1 最多 2 個，進階試算不做 |
| 各頁面自己寫公式 | 數字對不起來 | 一律呼叫 `FinanceCalcService` |
| Demo 當天資料壞掉 | 無法展示 | seed 一行指令重建 Demo 帳號 |

| 雲端費用 | 超出預算 | 設定預算告警，發表會後關閉 |
